# Zero-KV

Zero-KV is a hyper-optimized, zero-copy, disk-backed key-value storage engine built to achieve predictable, sub-50 microsecond P99 lookups. By pairing memory-mapped virtual file access with zero-overhead fixed-width protocol frames and vectored network I/O, the engine minimizes memory allocations and cuts out unnecessary context switches on the kernel hot path.

## Architectural Blueprint & Systems Flow

The engine operates as a highly synchronized pipeline between the pre-compiled disk storage, the virtual memory subsystem, and the Linux network stack.

### 1. The Disk Layout (The Static Blueprint)

The database structure relies entirely on an immutable, predictable binary layout generated by the compilation utility (baker):

* The Header (32 bytes): Contains structural metadata, starting with an engine magic identifier (0xA016) for validation and tracking item totals.
* The Index Section (Fixed-width): An ordered sequence of contiguous, 24-byte index structures. Because entries are identical in size and pre-sorted, lookups bypass scanning and use mathematical boundary calculations.
* The Data Section: Raw payload entries. Every boundary and data offset is guaranteed to be 8-byte aligned, allowing the CPU to load data into registers in a single clock cycle without manual byte-shifting.

### 2. The Runtime Lifecycle

When an inbound request strikes the interface, the server executes an allocation-free data pipeline:

1. Network Ingestion: The tokio network listener accepts the stream and spawns an isolated task. The engine immediately reads a fixed 16-byte buffer and uses zero-copy parsing to cast raw bytes directly into a structured layout without a deserialization loop.
2. Virtual Memory Lookup: Instead of loading database contents into heap memory (Vec), the storage core projects the database file straight into the process's virtual address space via mmap. The engine executes a binary search directly across the mapped index, returning a transient slice pointer pointing straight into the operating system's Page Cache.
3. Vectored Zero-Copy Outbound Path: The server prepares a response header on its local stack. Rather than merging the header and data slices into a new temporary buffer (which triggers memory allocation and copies data), it constructs a non-contiguous memory map array (IoSlice). It fires a single vectored write call, prompting the operating system kernel to collect data from both the stack and the page cache simultaneously, streaming it straight to the network interface card (NIC).

## Running the Architecture

### 1. Pre-Baking the Dataset

The engine requires a pre-compiled, sorted binary database file. Run the compilation utility to bake your data:
cargo run --bin baker

### 2. Launching the Storage Server

Boot up the asynchronous TCP engine to begin listening for incoming structured frames:
cargo run --bin kv_store

### 3. Verifying with the Test Suite

Execute the integration smoke test suite in an independent terminal window to validate successful round-trips and engine boundary conditions over active TCP sockets:
cargo test --test smoke_test
